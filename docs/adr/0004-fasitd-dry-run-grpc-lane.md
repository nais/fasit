# Fasitd dry-run uses a dedicated gRPC lane and separate persistence

We will introduce `fasitd` as a new agent alongside `naisd`. `fasitd` connects to Fasit over its own IAP-protected gRPC server on a dedicated port, using a long-lived **Fasitd session** keyed by tenant and environment. During dry-run, Fasit continues to publish the canonical deploy instructions to `naisd` over Pub/Sub, while also sending matching **Fasitd commands** over gRPC. `fasitd` command state, Helm logs, and release inventory are stored in separate `fasitd_*` persistence; `fasitd` health is represented by the live session itself rather than separate health messages or tables. Missing sessions are recorded as `fasitd` deployment problems rather than blocking the real `naisd` rollout. We chose this shape so we can validate the replacement transport and agent protocol without mixing experimental results into the current rollout truth or weakening the intended production auth model.
